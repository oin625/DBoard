# D板执行反馈

D板是用户的个人工作看板。开发需求使用 Dxxx，线上排查使用 Pxxx，两套编号各自递增；兼容已有 D 编号的排查任务，按 item.kind 选择流程。本机保存完整资料与历史，钉钉只同步总览和进度；不能用云端正文覆盖本机缓存。使用复制指令指定的 任务编号、绝对 CLI 和返回的缓存位置；云端 runner 通过用户 Mac 的本机工具执行。没有访问能力就说明未读取或未回写。

## 独立代码审查

返回 task 为 code-review 时，优先读 [CR规则](references/code-review.md) 或 guide --topic code-review。本轮只审查整体实现并记录结论，不继续开发、修复、改清单或测试阶段；即使开发已完成或已归档也执行审查。读取顺序为原咒言与全部追加变更→摘要与实际代码→有疑点才读相关历史。后面的普通“无待办则结束”、按历史覆盖补读和排查经验要求不适用本模式；没有摘要或摘要过时也不要求先读全部历史或重建摘要。压缩判断仍每次执行，推荐整理不等于CR必须整理。用 report --task code-review 保存审查概括与明细，绑定实际审查的代码版本；交接摘要可省略，保留原摘要与未覆盖记录，不把未读历史标为已覆盖。完成状态保持不变。只在明确CR任务时使用，不增加平时开发负担。

## 技术方案

需要方案设计、方案有变化或准备正式开发交付时，读 [技术方案规则](references/technical-plan.md) 或 guide --topic technical-plan，由AI提前维护本地方案。context --task technical-plan只生成／更新方案；关联正式需求的普通开发，在方案确定、实现完成或设计变化时核对technical_plan_state；方案缺失或失效时先按实际代码补写／更新，这属于交付准备，在“无待办则结束”前完成。无正式需求关联的小任务、线上排查及CR不强制生成。正文通过plan read按需读取，提交按钮只预览并使用已有有效方案。

## 线上排查与经验

只有 item.kind 为「线上排查」的任务，每轮 report 才须带经验判断 create/update/skip。先读 [排查与经验操作](references/incident.md)，查询候选经验并读取适用边界，再根据本次证据排查。普通开发需求不要求这个判断，也不自动写入排查经验库。

没有 任务编号、只是查询同类故障经验时，可通过本机 dboard-ai knowledge search 查询，再 knowledge read 读取选中的条目；不擅自新建任务或把旧案例当作当前任务。经验在 D板，Skill 只提供读写规则，查询不加载整个库。已完结排查只供查阅，不因有旧待办而恢复执行。用户明确要求完结本次排查时，可用 `incident close` 留一句实际结论并完成，详见排查操作；不自行完结，恢复由用户在D板操作。

## 接手与压缩判断

执行复制的 `dboard-ai context 任务编号`，核对编号、标题，读原咒言、追加变更、交接摘要、摘要之后的新记录和实时结构化状态。每次 context 都执行压缩判断并返回 `compression_check`，包括空历史、低于阈值和完整模式。AI 每次都须结合原因与内容决定 `compact` 或 `skip`；系统推荐为 false 也不能省略判断。

摘要是当前任务的接续状态：有效成果、待做与阻塞、仍适用的决定、验证边界及按需追溯入口。有实质进展每轮更新；整体整理淘汰过时结论、合并重复事实，把过程和证据移到读取入口。不设字数目标或上限，不因压短而丢失待办和约束，不重复原咒言、变更、仓库、清单和固定规则。每次按 review_questions 判断，累计10条记录只是自动提醒，也可因冲突、阶段切换或上下文压力提前整理；增量更新不重置整体整理计数。

原历史完整保留。没有摘要、覆盖失效或 history_read_required 为 true 时，先按返回命令读取所需历史明细，再接续。旧策略升级时核对现有摘要与相关原记录，不机械换字段。首次整理、压缩或反馈摘要时读 [交接与历史操作](references/handoff.md)，通过 reference_commands 或 guide --topic handoff 获取。默认不加载清单明细、证据和上一版全文；需要时按 context_sources 和摘要 resources 读取，未加载不等于为空。不额外调用模型做压缩。

用户最新补充、后续变更、清单调整和实际代码优先于摘要；用户“交接补充”保留原文，AI 不覆盖。纯交接补充不自动产生业务变更。摘要中的旧测试结论不能覆盖实时 `execution_needs_review`。

## 做什么与何时结束

只继续明确的未完成事项；检查实际代码，未记进度不等于未开发。没有待做且清单已核对时直接反馈，不重复开发、测试或自行新增优化。开发完成而待验收、人工联调或外部条件时，说明当前情况；联调填写区留空不产生任务。用户补充的真实联调报错是本轮排查任务，按证据定位、修复并复用已有页面。

追加变更优先于原咒言；指定 `--change C001` 时在已有实现上处理该条，概括带 `[C001]`。新版本仅把本轮变化写回指定新 任务编号，上一版是背景。最终内部／外部联调和验收由用户协调。

## 每轮反馈

每完成一轮有实质改动、排查结论或验证结果的工作，在结束前用 `report` 原子保存修改记录与更新后的摘要，同时带 `--compression-decision compact|skip` 和具体 `--compression-reason`。已保存的不重复追加；现状未变不重复记。仅需整理摘要时不加进度概括。反馈前重新读取最新 revision 并传 `--expect-revision`，摘要基于最新记录数；冲突时重读并合并，不能盲重试。见 [交接与历史操作](references/handoff.md)。

修改记录先一句话结果（通常20～60字、最多120字），再按需明细（通常1～3句）：关键验证、阻塞、下一步和证据入口。只记本轮变化，不塞完整背景、日志与路径。细节留资料或历史；不能把开发完成、AI试调通过、人工验收与上线混写成全部完成。

提交代码时 commit message 标题和正文用中文，保留仓库类型前缀和代码标识。只回写本需求实际开发仓库及开发分支；预发／发布工作树用--repo-role integration|release单独记录，不覆盖开发分支。上线清单保留工程原名，例如“发布 saleinventory 服务”，不翻译成中文别名。记录仓库、核验阶段或上线事项时读 [业务反馈操作](references/feedback.md)。核对或编辑清单前先通过 inspect --section release 读取完整明细与证据；清单为空、需复核或改动影响上线时核对补齐，保留用户修正、删除、证据与勾选；不自动发布、执行生产 SQL 或代勾选。

新需求和现有需求需要 Git worktree 时，先读 [工作树操作](references/worktrees.md)，统一用 `worktree create` 创建并立即登记，成功返回才在里面开发；已清理目录从主仓库保留的准确分支恢复。复用用 `register` 仅登记使用；其他工具已创建的目录立即 `register --created` 补齐。包括调试、集成和游离HEAD临时工作树，每轮结束核对本轮使用／创建的目录均已登记。台账独立保留全部目录，普通开发和CR不自动清理；由用户完结后预览确认。

正向核验必须绑定实际代码版本 `--expect-code`；代码或需求变化使旧结论失效，按实际核验更新或回退，不凭摘要重绑。用户选“无需调试页”时不建页、不撤销；`--task debug-page` 时读 [调试页规则](references/debug-page.md)，在 audi `/test-console` 增加入口并复用日志链，只试调 AI 能完成的部分。

## 确认保存

检查 JSON 的 `success`、`local_saved`、`sync`。`duplicate` 是相同事件已保存；重试保留原参数与 event-id。`unchanged` 是总览未变跳过上传；`skipped` 仅本地保存；本地已保存而同步失败时只重试 `sync`，不重加记录。

找不到、标题不符时停止该次回写，不新建替代需求。已完成时停止普通开发反馈；明确的CR可用专用模式追加审查结论，不恢复开发。普通开发需求完成由用户在D板操作：须清单全勾选、正式需求验收完成，空清单需二次确认。线上排查仅在用户明确指令后用 `incident close` 完结：留实际结论，不要求正式需求验收，有实际上线事项时仍须完成清单。轻量完结不要求重写摘要或重复经验判断；有尚未保存的新排查成果先正常report。除此之外，反馈权限不包含修改状态、优先级、周期、勾选、删除或归档需求。
