# D板独立代码审查

仅在 `context --task code-review` 或用户明确要求 CR 时使用。本轮交付是审查结论；不因为开发已完成、没有待办或已归档而跳过。原咒言、全部追加变更和用户纠正定义当前范围，摘要、旧测试与上一版只作线索。

## 读取顺序

1. 原咒言与全部追加变更：确定最终要求，后续变更优先。
2. 交接摘要、用户纠正和实际代码：理解现状并独立核对实现。最新记录只预览概括，摘要不能替代原始要求。
3. 相关历史明细：只有设计原因不明、信息冲突、证据不足或提交范围不清时，按关键词或指定记录追溯。

不默认读取全部历史；没有摘要、覆盖失效或新记录未纳入摘要，也不要求先补读全部记录或重建摘要。旧结论不确定就标注边界，结合原要求和当前代码继续审查。不能把未读历史当成已确认事实。用户明确请求完整历史时才使用 --full。

## 确定范围，再审查

核对需求关联的每个仓库和真实开发分支。结合记录、实际 Git 历史和方案确认本需求的起始提交与审查终点；必要时读 history 明细及 inspect code/background。不要默认 HEAD~1、主分支或合并分支就是基线，也不要把整个仓库历史算成本需求。范围不清先查证，仍不清则报告未覆盖部分及缺少的信息。

用只读 Git 命令检查整段 diff、暂存、未提交和未跟踪代码，再阅读相关入口、调用方与上下游实现；不能只看最新一次提交。逐仓库记录基线、终点、分支及工作区改动。当前工作区分支不符时优先查已有 worktree 或 git show，不切换、重置或清理用户工作区。

独立核对需求是否完整，重点看实际受影响的业务流程、接口兼容、幂等与重复请求、并发/事务、异常与外部调用、SQL/配置及发布依赖。按代码选择检查项，无关项不凑清单。需要验证疑点时运行最小范围的针对性测试；不默认跑全量回归，也不操作生产业务。

每个确认问题写：严重程度、文件与行号、触发条件、影响、关键证据和建议。区分本次引入的问题、相关历史缺陷与待确认疑点；不把风格偏好、假想需求或缺少外部验证包装成确定 Bug。过度设计只在确实增加维护成本或引入风险时点出，不为简化重写业务。

## 结论与反馈

先用一句话给结论：发现问题／已审范围未发现确定问题／审查受限，再按问题分条写明细。无问题也交代审查范围、必要验证与未覆盖边界；CR不等于测试验收完成。默认不改代码、分支、调试页、上线清单或需求状态，修复须用户另行要求。

结束前重新 show，核对需求 revision、追加变更与 code_revision 和审查时一致；若变化先审查增量，不把新版本号绑定给旧结论。每次仍判断 compact/skip；系统推荐压缩不要求本轮先整理历史，按审查需要判断并说明理由。

默认只追加本轮CR概括与明细，可省略 --handoff-file，保留原摘要、覆盖位置和未覆盖历史。缺少摘要也允许这样反馈，不编造四段摘要来绕过读取边界。只有确实掌握当前接续状态且需要更新摘要时，才按 handoff 规则提供四段；若要整体整理，须先核对相应历史，不能把未读记录标为已覆盖。

用现有 report 的专用模式保存一句话概括与本地明细，包括已完成需求。该模式只允许审查记录和交接，不回退开发或测试阶段，也不要求线上排查经验收集。概括带 [CR]，明细写各仓库基线/终点、确认问题、验证和未覆盖内容；远端只同步概括。

```bash
dboard-ai report D014 --task code-review --review-result findings \
  --expect-title '最新标题' --expect-revision '最新revision' --expect-code '实际审查的code_revision' \
  --summary '[CR] 发现一处重复锁券风险，待确认后修复。' \
  --details 'ultra：基线…，终点…；工作区…。问题位置、触发条件与证据…。已验证…；未覆盖…。' \
  --compression-decision skip --compression-reason '已更新审查发现和边界，接续状态明确，无需整体整理。' \
  --event-id 'D014-cr-20261106-01'
```

使用 context 给出的绝对 CLI 与 cache。clear 表示已审范围未发现确定问题；findings 表示存在确认问题；limited 表示范围或验证不足。无法核实全部仓库版本时只允许 limited，省略 --expect-code 并说明原因。能核实版本时三种结果均传实际审查的 --expect-code。保存失败按错误重读；本地保存而同步失败只重试 sync，不重复添加记录。已完成状态不因CR问题自动恢复，由用户决定后续处理。归档快照是旧版本关联的身份，不修改原快照；同一 report 命令会把归档CR结果单独存入本机，在已完成卡片展示最近概括，点开查看明细；归档CR不上传远端，反馈的交接也留在这条审查记录中。

方法参考：[Superpowers requesting-code-review](https://github.com/obra/superpowers/tree/main/skills/requesting-code-review) 的需求对照、完整 Git 范围和具体问题证据；本地 receiving-code-review 的先核实再接受意见。规则随 D板打包，无需额外安装这些 skills。
