## 上线前事项

每轮先读当前 `item.release_checklist` 的概括、勾选和维护状态。核对、编辑或判断证据前，按 context_sources.release 执行 `inspect 任务编号 --section release` 取得最新完整清单；未加载的明细与证据不等于为空。清单为空、`needs_review` 为 true 或本轮实际改动影响上线时，结合本需求实现、Git 改动和方案核对具体上线动作，并在结束前更新。一条一个可执行动作，分为「短概括」和可选「明细」。服务发布项保留实际工程名及大小写，不翻译成中文业务别名，例如“发布 saleinventory 服务”“发布 ultra 服务”；已有中文别名项核对实际工程后按权限改正，用户维护项先保留。概括只写做什么，通常 6～20 字，最多 40 字，例如「发布 ultra 服务」「执行高德建表 SQL」「配置归因定时任务」；分支、提交、SQL 路径、配置参数、前置条件和执行顺序都写进明细，通常 1～3 个简短段落，不塞进概括，也不粘贴日志。不要复制通用发布清单、把联调待办当上线动作或猜测生产信息。核对和补齐这份清单属于本需求的准备工作，即使开发已完成也按需处理；清单中的未勾选项不授权自动发布、执行生产 SQL 或重新开发。

按动作分类：`release`（发布服务／前端）、`sql`（建表、索引及数据 SQL）、`configuration`（配置、开关和定时任务）、`permission`（接口授权、角色及菜单权限）、`other`（其他上线动作）。这些只是常用分类，上线动作不局限于这几种。必要时用 `custom:分类名称` 新建贴合本需求的分类，例如 `custom:资源准备`、`custom:数据迁移`、`custom:监控告警`（名称 1～20 字）；先复用清单已有分类，避免同义分类重复或把每个事项都单独分类。不同类型的动作分别列项；分组只用于展示，实际执行顺序写明细。用户可以调整分类，下次接手以最新分类为准。

用 `--release-item '{"summary":"发布 ultra 服务","category":"release","details":"开发分支：feature/xxx。先执行建表 SQL，再发布服务。"}'` 写入；明细可省略，多个事项重复参数。修改时带事项编号，如 `--release-item '{"id":"L001","summary":"执行高德建表 SQL","category":"sql","details":"SQL 文件和建表说明"}'`；未传 category 或 details 时保留原值。旧命令 `report --release-add '发布 ultra 服务'` 仍可用，未指定分类会按概括推断。`--release-edit 'L001=简短概括'` 只改概括并保留明细；`--release-remove L001` 删除事项。仅修改自己维护且未完成的项。D板默认只显示概括，点击明细才展开，后续 AI 默认只加载概括与状态，通过 `inspect --section release` 按需读取完整明细。反馈前 `show` 取最新 revision，保留用户增删改和勾选结果；`updated_by: user` 的项及 `excluded_by_user` 中用户删除／修正的旧文字不要覆盖或原样补回。追加变更带来的新发布动作另加具体事项，可注明变更编号，保留旧完成项。CLI 按项更新、去重并保护用户维护的项，不通过整份列表覆盖来绕过这些规则。

核对后传 `--release-reviewed`，可与清单参数、概括或开发核验阶段一起反馈，也可单独使用。确实没有上线前事项时允许清单为空，只记录核对结果；已核对且需求、代码均未变化时不重复补充或凑条目。`release_result.skipped` 会说明已有相同事项或用户曾删除／修正，不将跳过视为添加成功。清单完整保存在本机，下一次 `context` 会读取用户修改后的最新内容；勾选由用户决定，不把生成 SQL 或提交代码等同于已上线执行。清单中的 `evidence` 是用户留存的完成证据，支持文字和本机图片；按需查看，保留原文和图片，不覆盖、删除或凭图片自行勾选。

## 开发核验与调试页

先看 `item.debug_page_not_needed`：为 true 时，用户已手动选择无需调试页，不创建、更新或删除页面，也不自行撤销；最新选择覆盖旧咒言和旧复制指令的建页要求。它只免除页面，后端核验、接口测试和人工联调仍按需进行；通过 `development-complete` 和普通概括／明细记录验证，不回写页面就绪或页面试调阶段。追加变更不会自动撤销选择，已有页面和结果留作参考，用户撤销后再接续页面任务。

`context --task debug-page` 是用户明确发起的 audi 调试页面任务。读取返回的 `debug_instructions`（来自 [调试页规则](debug-page.md)），核验后端开发后在 audi `/test-console` 增加模块入口，并复用 `DebugLogChain` 展示本次请求的服务日志、关键步骤与异常（接入方式见调试页规则）；开发完成后仍需接续这项页面任务。AI只先调能独立验证的部分，最终内部／外部联调测试由用户协调进行。页面及AI可调部分已完成，剩余需人工联调时，交接后直接反馈，不重复建设或反复尝试外部条件。

通过 `report --stage` 记录 `developing`、`development-complete`、`debug-page-ready` 或 `testing-passed`；正向核验结果须有一句话概括和必要的实际依据明细。普通开发任务确认实现完整时也可记录 `development-complete`，不因此自动创建调试页。页面用 `--debug-page` 回写实际路由，确认可访问后可补 `--debug-url`。`testing-passed` 仅表示AI能独立验证的部分通过，必须记录已测、未测和待人工联调事项，不能表示整体联调完成。这些是执行结论，独立于用户完成、验收和归档；需求变更后旧结论需重新核验。代码后来改变或发现失败时主动回退可靠阶段。

每个正向阶段都绑定已记录开发仓库的分支、提交和未提交内容（含未跟踪文件）。先分别回写本需求实际修改的仓库，再核验；页面任务也须记录 audi。核验结束后 `show` 取最新 `item.code_revision`，在正向 `report --stage` 中传 `--expect-code '<code_revision>'`；无提交、仓库不可读或代码在反馈前又变化时，不写通过。提交代码也会改变版本，提交后再读版本并确认验证仍适用。`execution_needs_review` 为 true 时看 `execution_review_reason`：旧结论未绑定、需求或代码改变都只作历史参考；先记录 `developing` 或重新核验受影响的实现、页面及测试后更新可靠阶段，不能只凭旧通过结论结束，也不能未验证就重绑版本。普通进度反馈不会刷新代码核验。没有实际新任务时只核对并反馈失效原因，不自行扩大开发范围。


## 仓库与反馈
需求概括缺失或改造范围有变化时，可额外传 `--overview '一两句话概括当前需求范围'`（单行，最多 120 字）；概括只说明需求范围，不写路径、过程或整份咒言。已有概括且范围未变时不用反复更新，也不需要用户另填一份材料。概括与进度可分别反馈。

仓库与进度可以分开反馈：只传 `--repo` 记录仓库和分支，传 `--summary` 和可选 `--details` 追加记录（旧参数 `--progress` 等同 `--summary`）。多个仓库各自反馈；同一 Git 仓库只保留最新反馈的源开发目录与分支。预发兼容／集成和发布工作树用--repo-role integration或release另行记录，不能覆盖源开发分支；名字用途不明先核对，明确的源开发工作树使用--repo-role development。历史留在进度中。分支展示用工程名，不把多个工作目录当作多个工程。迁移、清理或切换工作目录后须回写实际仓库与分支；旧目录已不存在且确认代码移至新目录时，用 `--repo '/新目录' --replace-repo '/原记录目录'` 明确替换。仅阅读参考仓库不必反馈为开发仓库，不能把其他任务当前所在的分支当成本需求分支。CLI 不创建或切换 Git 分支；这些操作属于原开发任务。

创建与复用的工作树按 [工作树操作](worktrees.md) 立即登记。仓库字段保留最新目录，工作树台账保留全部目录及归属，互不替代。普通 `report --repo` 自动登记使用，创建归属须用 `worktree register --created` 明确声明；普通反馈不自动清理。

相同反馈重试时保留原参数和同一个 `--event-id`；不同反馈用新编号。工具会防止重复追加，不要通过改写整份 Markdown 绕过 CLI。
