# 技术方案与开发交付

D板的技术方案由执行 AI 根据原咒言、全部追加变更、用户纠正和实际代码维护。D板按钮只读取、预览和提交已准备的方案，不调用模型、不把历史记录拼成正文。

## 何时维护

普通开发需求进入方案确定阶段时先形成方案；实现、接口、数据或兼容策略变化时更新。关联正式需求且准备开发交付时，方案缺失或返回 technical_plan_state.needs_review 为 true，核对已有方案和代码，再保存有效版本。仅代码版本变化并不证明设计变化：核对影响后可保留正文并更新绑定。无方案变化、无新任务时不重复生成。线上排查、独立CR和无需正式交付的小任务不因此强制生成方案。

明确 context --task technical-plan 时，本轮只准备方案；即使开发已完成也执行，不恢复开发或发布。读取顺序：原咒言与全部追加变更→用户纠正、摘要、已有方案及实际代码→有疑点再按需读相关历史。不默认读取全部历史或为写方案先重建摘要。每次context仍判断压缩；压缩推荐不是写方案的前置任务。

## 写什么

写清改造目标、涉及工程、核心流程与实现、接口／数据／配置变化、兼容与上线注意事项、验证边界。按需求选择必要章节，不凑空章节；段落简短，复杂关系可用表格或小流程。保留重要边界、失败处理与依赖关系，不设字数目标，也不粘贴完整日志、历次commit、CR流水或一长串类方法清单。已经实现、尚未实现和待确认明确区分；旧方案被后续变更替代时更新正文。方案不是验收结论，不能把AI可测部分通过写成整体联调完成。

先通过 plan read 任务编号读取最新正文、revision和作者。用户编辑的正文保留其有效纠正，需求或代码冲突先说明，不用旧AI稿整篇覆盖。项目名保留实际工程名。

## 分支用途

--repo 默认记录源开发工作树；预发兼容、集成或发布工作树使用 --repo-role integration 或 release，分开记录，不覆盖开发分支。名字含pre不必然是合并分支，必须结合来源及用途判断，不能只凭feature前缀判断。开发工作树明确时使用 --repo-role development。预发上的独有业务修复若应进入源开发分支，先确认并完成原任务授权的同步，再记录源分支；不能用改标签掩盖代码差异。

方案 projects 为本需求实际开发工程和源分支（name、branch），与D板记录逐一匹配。预发／发布分支在方案的兼容或上线说明中写明用途，不能进入开发交付工程字段。不能把参考仓库、其他需求当前分支或整个pre基线当作本需求开发范围。

## 保存

执行 plan read 任务编号；写UTF-8 JSON文件：title、markdown、projects（每项name和branch）。用本机允许的文件工具写文件，再执行：

dboard-ai plan save D014 --file /绝对路径/technical-plan.json --expect-title 'show返回的标题' --expect-revision '最新需求revision' --expect-code '核对后的code_revision' --expect-plan 'plan read返回的plan.revision'

首次 --expect-plan 为 none。代码尚无法核实的设计草稿可省略 --expect-code，但不能提交开发交付。保存绑定当前需求、代码和工程分支，原子追加一句话记录，正文仅本地保存；不会自动上传钉钉或提交交付物。同内容重复保存不追加记录。保存冲突时重读并保留用户修改，不盲重试。已有方案仅重新核对代码时也须核对实际差异，不能未读代码就重绑。plan save自身已记录方案更新，不再重复report同一事件；普通业务进展仍遵循主Skill反馈。

用户点击提交开发交付后，D板展示方案与源开发分支供核对，确认后保存文档到指定目录并提交。发现远端文档被他人编辑时保留远端内容并提示核对，不能自动覆盖。不要为生成方案自行提交需求流或执行上线动作。
